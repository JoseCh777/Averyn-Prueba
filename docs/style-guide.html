Reglas de uso — qué sí y qué no

Tener el componente correcto no sirve si se combina mal. Estas son las reglas que más se rompen.

Jerarquía de botones

Sí

Un solo av-btn-primary por pantalla/modal: la acción principal. El resto son secondary o ghost.

No

Dos primary juntos compiten por la atención — el usuario no sabe cuál es la acción esperada.

Uso de color semántico

Sí

av-btn-danger solo para acciones destructivas e irreversibles.

No

Rojo en "Cancelar" asusta al usuario por una acción que no destruye nada. Eso es un ghost o secondary.

Alertas vs. Toasts

Sí

av-alert: estado permanente de la pantalla (ej. "documento rechazado").
av-toast: confirmación pasajera de una acción (ej. "cambios guardados").

No

Usar un av-alert que desaparece solo a los 3 segundos, o un toast que se queda fijo explicando un estado del formulario. Cada uno tiene un solo trabajo.

Espaciado y color libre

Sí

Usar siempre variables: var(--av-space-4), var(--av-blue), var(--av-radius-md).

No

Escribir valores sueltos como margin: 18px o color: #1560ef. Si el token que necesitas no existe, se propone (ver Gobernanza), no se inventa en el momento.

Regla general

Si tu pantalla necesita un componente, variante o color que no está en este catálogo, no lo crees por tu cuenta: revisa la sección Gobernanza al final de esta página.

9. Selects

Misma caja que el input (altura 44px, radio, focus) para que convivan en un mismo formulario.

10. Checkbox, Radio y Switch

Checkbox: selección múltiple. Radio: selección única visible. Switch: on/off inmediato (no requiere botón "Guardar").

11. Tabs

Para cambiar de vista dentro de una misma pantalla, no para navegar entre módulos (eso es el navbar).

Gobernanza — proceso de cambios

Este documento es la única fuente de verdad de diseño de Averyn. Ninguna pantalla del producto debería tener un componente, color o espaciado que no esté aquí.

  1. Si necesitas un componente, variante o color que no existe en este catálogo, no lo crees directamente en tu bloque (A, B, C o D).
  2. Propón el componente al equipo (mensaje o reunión corta) mostrando el problema que resuelve.
  3. Se agrega a design-system.css y a este catálogo con su número de sección correspondiente.
  4. Solo después de estar aquí, se usa en el producto.
  5. Antes de la sustentación: cada integrante revisa su bloque contra este documento y confirma que no hay clases ni estilos inline que no estén catalogados.

Accesibilidad — checklist mínimo

Aplica a cualquier pantalla nueva, sin excepción.

  • Todo elemento interactivo es alcanzable con Tab y muestra el anillo de foco azul (nunca se remueve :focus-visible sin reemplazo).
  • Iconos que son la única pista de una acción (cerrar, alerta) llevan aria-label.
  • El modal se cierra con Esc, clic fuera, y el foco vuelve al botón que lo abrió.
  • Contraste mínimo AA: texto normal 4.5:1, texto grande/íconos 3:1 — los colores semánticos de este catálogo ya cumplen, no se aclaran ni oscurecen "a ojo".
  • Los estados vacíos y de carga siempre llevan texto, nunca solo un ícono o spinner suelto.

Formato de datos

FechaDD/MM/AAAA en toda la interfaz, sin excepción.
DocumentoTal cual lo ingresó el usuario, sin puntos ni guiones añadidos.
Confianza biométricaNunca el número crudo (ej. 87.3421%). Redondear a entero o usar etiqueta cualitativa ("Alta coincidencia").
NombresTal cual vienen del documento oficial — nunca forzar mayúsculas.

Referencia rápida

  • Botones: verbo corto ("Guardar cambios", "Ingresar") — nunca "OK" o "Enviar" a secas.
  • Tuteo siempre, nunca "usted".
  • Todo mensaje nuevo que no esté en las tablas de arriba se propone antes de usarse (ver Gobernanza).
